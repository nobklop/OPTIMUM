# Правила разработки OPTIMUM

- Качество и законный доступ к аудио важнее количества функций.
- Выполнять законченные проверяемые этапы; не выдавать domain tests за сетевую интеграцию.
- Не добавлять fake users, fake recommendations, неработающие кнопки или фальшивые статусы.
- Сначала изучать затронутые файлы адресно; выбирать простое решение в текущей архитектуре.
- Рутинные обратимые решения принимать самостоятельно; уточнять существенные неизвестные.
- Не публиковать и не изменять чужие сервисы без нужной авторизации; не коммитить секреты.
- Аудиофайлы пользователя не удалять; опасные миграции только с backup и rollback.
- Проверки: `flutter analyze`, `flutter test`, backend pytest/ruff; сборки реальных платформ
  отдельно. Успешные проверки не повторять без изменений или новых рисков.
- UI проверять настоящими кадрами Flutter; требование отдельных кадров Godot относится
  к изменяемым игровым элементам, которых в этом приложении нет.
- После этапа обновлять README/ROADMAP/CHANGELOG/ARCHITECTURE и verification, сохранять Git.
- Длительную работу фиксировать в `docs/SESSION.md`: решения, файлы, проверки, остаток.
- Общаться кратко на русском, явно сообщать ограничения и неподтверждённые платформы.
